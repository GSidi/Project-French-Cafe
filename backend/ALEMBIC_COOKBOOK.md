# Alembic cookbook

Copy-paste commands for this project. See `BACKEND_ARCHITECTURE.md` for the *why*
behind the base/models/database split, and `DATA_MODEL.md` for the schema itself.

## Rule zero: always run from `backend/`

`alembic.ini` sets `prepend_sys_path = .`, which resolves against the **current
working directory**, not the ini's location. Running `alembic -c backend\alembic.ini`
from the repo root still fails with `ModuleNotFoundError: No module named 'app'`.

```powershell
cd "C:\Users\George\Desktop\Cafeteria's Project\backend"
.\.venv\Scripts\Activate.ps1
```

Prompt should now read `(.venv) PS ...\backend>`. Every command below assumes that.

## Preflight: is the database actually up?

Docker Desktop running does **not** mean the container is running — `cafe-db` has
exited on its own before. The tell is `/health` hanging while `/docs` still works.

```powershell
docker compose ps          # run from the repo root; STATE should be "running"
docker compose up -d       # if it isn't
```

If port 5432 misbehaves, check for the native Postgres service stealing it **first** —
it produces a misleading `password authentication failed for user "cafe"`, because
Postgres says that for a *nonexistent* role too:

```powershell
Get-NetTCPConnection -LocalPort 5432 | Select-Object OwningProcess
Get-Service postgresql-x64-18        # should be Stopped / Manual. Keep it that way.
```

## The standard add-a-table loop

```powershell
# 1. Where am I? Confirms Alembic can reach the DB and which revision it's on.
alembic current

# 2. Generate a revision from the diff between models.py and the live DB.
alembic revision --autogenerate -m "add staff_assignments"

# 3. READ THE GENERATED FILE in alembic/versions/ before doing anything else.
#    Autogenerate is a first draft, not an answer. See "what to check" below.

# 4. Render the SQL without touching the database. Catches CREATE TYPE collisions
#    and other surprises while they are still free to fix.
alembic upgrade <current_rev>:head --sql

# 5. Apply for real.
alembic upgrade head

# 6. Prove it round-trips. Non-negotiable for a migration you intend to keep.
alembic downgrade -1
alembic upgrade head
```

In step 4, `<current_rev>` is what `alembic current` printed in step 1 — i.e. the
revision *before* the new one. Using `head:head` renders nothing.

## What to check in every autogenerated migration

1. **Duplicate `CREATE TYPE`.** If the new table reuses an enum an earlier migration
   already created, autogenerate re-emits `sa.Enum(...)` and the upgrade dies with
   `type "x" already exists`. Sharing one `SQLEnum` object in `models.py` does *not*
   prevent this — it only dedupes within the model file. Fix by hand:
   ```python
   postgresql.ENUM("FREE", "OCCUPIED", name="table_status", create_type=False)
   ```
   (with `from sqlalchemy.dialects import postgresql` at the top of the migration).

2. **Enums are never dropped on downgrade.** Autogenerate drops the table and leaves
   the type orphaned. Hand-add to `downgrade()`:
   ```python
   sa.Enum(name="status_source").drop(op.get_bind())
   ```

3. **Enum *value* changes are invisible to autogenerate.** Adding a member to a
   `StrEnum` produces an empty migration. Hand-write it:
   ```python
   op.execute("ALTER TYPE table_status ADD VALUE 'RESERVED'")
   ```

4. **Constraint renames become drop + create.** Functionally correct, but it rebuilds
   the index for nothing. Replace with the metadata-only version:
   ```python
   op.execute("ALTER TABLE tables RENAME CONSTRAINT old_name TO new_name")
   ```

5. **An empty `upgrade()` usually means the diff was not what you thought.** Alembic
   compares `__tablename__`, not the Python class name — renaming a class is invisible
   to it and correctly needs no migration.

6. **Migrations never import from `app.models`.** A migration is a frozen snapshot of
   the schema at one point in time; enum values and column types are inlined on
   purpose. If the models change later, old migrations must not change with them.

## Inspecting the result

```powershell
alembic current              # revision the DB is on
alembic history --verbose    # full chain
alembic heads                # >1 head means a branch that needs merging
```

For real DDL, use pgAdmin 4 (`C:\Program Files\PostgreSQL\18\pgAdmin 4\runtime\pgAdmin4.exe`):
navigate to the table, then the **SQL** tab. That is Postgres telling you what it
actually built, which is the only authority that matters.

## Gotchas that are not Alembic's fault

- **PyCharm's Python Console caches `app.models`** in `sys.modules`. Edits made after
  the module was first imported will not show up. Restart the console — expect this
  every single time you add a column.
- **`settings.database_url` is lowercase.** Uppercase is the `.env` convention only.
- **`alembic.ini`'s `sqlalchemy.url` stays as the placeholder.** The ini is committed;
  `env.py` supplies the real URL from `settings`. Do not fill it in.
